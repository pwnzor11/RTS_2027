# C&C Maps, Terrain Templates, Tiberium/Ore Economy and the C# Map Editor

## Summary

- A Tiberian Dawn (TD) map is a fixed 64x64 array of cells (128x128 in Red Alert). Each cell stores a terrain template id plus icon index (the "BIN" layer), an overlay id plus one data byte (resources, walls, crates), a smudge, and visibility bits. Land type (clear, road, water, rock, wall, tiberium, beach) is derived and cached from those fields.
- Terrain is tile-set based. A template is a W x H block of cells (up to 13x8) whose individual icons each map to one cell. Land type comes from the template default plus a per-icon exception list. TD has 217 template types across 4 theaters (desert, jungle, temperate, winter).
- A scenario is a plain INI (names, cell numbers, comma lists) plus a 8,192-byte `.BIN` (two bytes per cell). Objects reference triggers and teams by name, and cells by index (y*64+x). Load order is dictated by those references.
- Tiberium is an overlay: 12 visual variants, but the real amount is the cell's `OverlayData` (0..11, worth (n+1)*25 credits). Growth and spread are a slow background sweep, 30 cells per frame; each full sweep (~9 s) grows 2 cells and spawns 2 new ones. Harvesters ring-search outward, scoop up to 6 steps per second, carry 28 steps (700 credits) and unload bail by bail at the refinery. Credits split into a capped silo pool and an uncapped cash pool, and harvest overflow is simply lost.
- RA differs materially: ore grows everywhere on a timer (all eligible cells step each cycle), only gold grows and spreads (gems do not), and the harvester dumps its whole load at once.
- The C# editor (WinForms, .NET Framework 4.6.2, GDI+) is cleanly layered (IGamePlugin, Map model, Tools, MapRenderer), but it cannot run without the paid Remastered game's MEG texture archives, and it ships with a Steam Workshop publisher. It is a useful design reference, not a good fork base.

Caveat: the repository contains no game data (no `.INI`, `.BIN` or `.MIX` files), so the INI examples below are constructed from the parsers, not copied from shipped missions. Section 6 is therefore reasoning from structure, not measurement.

## 1. Map representation

**Grid.** `MAP_CELL_W/H` are `1<<6` = 64 in TD (`DEFINES.H:269-277`), 128 in RA (`REDALERT/DEFINES.H:514`). A `CELL` is a single integer, `x + y*64`. A cell is 24x24 pixels (`DISPLAY.H:42-47`) and 256 "leptons" wide; objects position themselves in leptons, so they are not cell-locked.

**Playable rectangle.** The array is always full size, but `[Map]` defines the playable window: `X`, `Y`, `Width`, `Height`, defaulting to 1,1,62,62 (`DISPLAY.CPP:1307-1310`). Everything outside is a border: overlays are refused on the top and bottom rows (`OVERLAY.CPP`), `Sight_From` and the crate placer test `In_Radar`/the window, and harvester search rejects cells outside the window (`UNIT.CPP:2323-2331`). Off-map cells are where reinforcements spawn and where units exit.

**What a cell stores** (`CELL.H:55-190`): packed flag bits (mapped, visible, has-trigger, has-waypoint, flagged, cursor); `TType`/`TIcon` (terrain template and which icon of it); `Overlay`/`OverlayData`; `Smudge`/`SmudgeData`; `Owner` (for walls and smudges); occupant pointers; a 8-bit sub-position occupancy mask (centre plus four infantry corner spots plus vehicle/monolith/building); and two 32-bit per-player visibility masks added by the Remastered port. The derived `Land` field is not saved.

**Templates and tiles.** Each `TemplateTypeClass` (`TYPE.H:1457`, instances in `CDATA.CPP:81-2480`) has a name, a theater bitmask, `Width x Height` in icons, a default `Land`, and an exception pair `AltLand`/`AltIcons`. An icon set file (e.g. `FORD1.TEM`) contains the pictures plus an icon map that marks which of the W*H slots exist (255 = hole, so templates can be non-rectangular). Example: a 3x3 river-ford template is `LAND_WATER` by default, with `AltIcons` listing the indices that are `LAND_CLEAR` (shore slopes). `CellClass::Recalc_Attributes` (`CELL.CPP:488-540`) works out the land: overlay land wins if it is not clear (walls, tiberium); otherwise the template's `AltIcons` list is searched; otherwise the template default; no template means clear.

**Passability** is a table, not code: `Ground[LAND_COUNT]` (`CONST.CPP:262-276`) gives each land type a speed multiplier (0x00..0xFF) per locomotion class (foot, tracked, harvester, wheeled, winged, hover) plus a "can build here" bool. Water and rock are 0x00 for every ground class and 0xFF for air. Road is fast, clear and tiberium medium, wheeled is a bit faster than tracked on clear ground. Pathfinding reads this table, so choke points are simply rock or water templates.

**Theaters.** `Theaters[]` (`CONST.CPP:282`) gives each theater a name, a mix-file name and a 3-letter suffix. TD: DESERT, JUNGLE, TEMPERATE, WINTER; RA: TEMPERATE, SNOW, INTERIOR. On load, `TemplateTypeClass::Init(theater)` (`CDATA.CPP:2595`) builds a filename like `FORD1.TEM` and fetches that icon set from the mix archives; types not flagged for the theater get no image. The theater also gates which terrain objects (trees, rocks), overlays and smudges exist. The cost of switching theater is thus "reload all art", not a different rule set.

**Waypoints** are a flat array of cell numbers (`Waypoint[WAYPT_COUNT]`). In TD: 0-25 are lettered/numbered general waypoints (the editor labels 0-7 as player starts P0-P7, which multiplayer uses as start locations, `INI.CPP:1685-1700`); 25 is also where the "LZ smoke" flare animation appears (`TRIGGER.CPP:472`, editor name "Flare"); 26 `WAYPT_HOME` is the initial camera/home cell (defaults to the map's top-left if absent, `DISPLAY.CPP:1366`); 27 `WAYPT_REINF` is where reinforcement transports arrive (`AIRCRAFT.CPP:1198`). Team missions refer to waypoints by number (`TEAM.CPP:497`). RA has 98 + HOME/REINF/SPECIAL (`REDALERT/DEFINES.H:3546`).

## 2. The scenario file format

Two files per mission: `NAME.INI` and `NAME.BIN`. `Read_Scenario_Ini` (`INI.CPP:210-680`) loads in this order, and the order encodes the reference graph:

1. `[Basic]`: movie names (`Intro`, `Brief`, `Win`..`Win4`, `Lose`, `Action`), `Theme`, `Player` (`GoodGuy`/`BadGuy`), `CarryOverMoney` (percent), `CarryOverCap`, `BuildLevel` (tech level). `BuildLevel` is how campaign tech unlocks per mission.
2. `[TeamTypes]` first, because triggers point at teams. One line per team: `Name=House,Roundabout,Learning,Suicide,Autocreate,Mercenary,RecruitPriority,MaxAllowed,InitNum,Fear,ClassCount,Class:Num,...,MissionCount,Mission:Arg,...` (`TEAMTYPE.CPP:240-258`). Missions that target a place use a waypoint number as the argument.
3. House sections (`[GoodGuy]`, `[BadGuy]`, ...): `Credits` (the code multiplies by 100, `HOUSE.CPP:1907-1930`), `Edge` (reinforcement/spawn edge: North/East/South/West), `Allies`, `MaxUnit`, `MaxBuilding`.
4. `[Triggers]`: `name=Event,Action,Data,House,TeamName,Persistence` (`TRIGGER.CPP:1115-1150`), e.g. `win1=Destroyed,Win,0,GoodGuy,None,0`.
5. `[Map]`: `Theater=TEMPERATE`, `X=1`, `Y=1`, `Width=62`, `Height=62`. `[Waypoints]`: `0=2330`, `26=2000`. `[CellTriggers]`: `cell=triggername`, so that "player entered" fires.
6. The `.BIN` (below). If it is missing, a legacy `[TEMPLATE]` section (`cell=TEMPLATENAME`) is used instead.
7. `[TERRAIN]` (trees, rocks; `cell=TYPE,trigger`), `[UNITS]`, `[AIRCRAFT]`, `[INFANTRY]`, `[STRUCTURES]`: key is a unique id, value is `House,Type,Strength,Cell,Facing,Mission,Trigger` for units (`UNIT.CPP:3802-3840`). Infantry adds a sub-cell spot (0-4) and puts mission before facing; structures omit mission. Strength is 0-256 (256 is full health). Example: `3=GoodGuy,MTNK,256,2330,64,Guard,None`.
8. `[Base]`: `Count=n` then `000=PROC,coord` ... a pre-planned build order the AI replays (`BASE.CPP:133`).
9. `[OVERLAY]`: `cell=TI3` (tiberium), `SBAG`, `BRIK`, crates, etc. `[SMUDGE]`: `key=TYPE,cell,data`. `[Briefing]`: numbered lines concatenated.
10. `Map.Overpass()` (`MAP.CPP:595`): post-pass that re-randomizes the tiberium variant and recomputes each tiberium cell's density from its neighbours (see 3).

Hard-coded campaign hacks also live in the loader (`INI.CPP:541-600`: forcing particular cells to rock on named missions). That is a lesson: do not let such patches live in code.

**The BIN.** Exactly 4096 pairs of bytes in cell order: `TemplateType` (255 = none) and icon index (`MAP.CPP:646-724`). Load validates each pair against the icon set's hole map and falls back to clear on error. The CRC of the INI text plus the BIN contents is folded into `ScenarioCRC` for multiplayer sync.

**Name references.** Everything is by short uppercase name resolved at load (`From_Name`): house, unit, trigger, team. Triggers are attached by name to cells, units, buildings, infantry and terrain objects and ref-counted with `AttachCount`. A trigger naming a nonexistent team simply loads as null; there is no validator in the game, only in the editor.

## 3. Resources

### Tiberium as cell state
Tiberium is an overlay, but two separate things are stored: which of 12 overlay types (`OVERLAY_TIBERIUM1..12`, names `TI1..TI12`) is displayed, which is purely a random visual variant (`CELL.CPP:1894-1898`), and `OverlayData` 0..11, the density. A cell is worth `(OverlayData+1) * 25` credits (`TIBERIUM_STEP` = 25, `TYPE.H:862`), so a full cell is 300. `Tiberium_Adjust` (`CELL.CPP:1885`) sets initial density from how many of the 8 neighbours are tiberium via a lookup `{0,1,3,4,6,7,8,10,11}`: edge cells are thin, interior cells are rich. Mapmakers therefore only paint where tiberium exists and the engine shapes the density.

### Growth and spread (TD, `MAP.CPP:897-1040`)
`MapClass::Logic` runs every frame. It scans 30 cells per frame, so a full map pass is 4096/30 = 137 frames, about 9 s at 15 ticks per second. During the scan it collects candidate cells into two 50-slot arrays: **growth** candidates (tiberium cells with density < 11) and **spread** candidates (density > 6, plus blossom trees, which count three times). Overflow replaces a random slot. When the scan wraps, it applies `tries` changes: by default 2 (`IsTFast` is on in `Special.Init`, and multiplayer forces 2; the Remastered multiplayer "Tiberium" option adds more). Each growth pick adds one density step to a random candidate; each spread pick finds a random adjacent cell that is clear, empty and not a bridge and plants a new overlay at density 1. The scan direction flips each pass. So whole-map growth is tiny (about 13 steps a minute) and strictly local: mature fields creep outward and thicken, and blossom trees seed new patches. Tiberium also hurts: infantry take 2 damage per cell tick on it except chem-warrior E5 (`INFANTRY.CPP:777-782`), and explosions chew density (`Reduce_Tiberium(strength/10)`, `COMBAT.CPP:223`).

### Harvesting (TD)
- Constants: 28 steps carried (`STEP_COUNT`), 25 credits each, so 700 per full load (`TYPE.H:862-864`).
- `Mission_Harvest` (`UNIT.CPP:2707`) is a state machine: LOOKING, HARVESTING, FINDHOME, HEADINGHOME. Selection is `Goto_Tiberium` (`UNIT.CPP:2347`): if standing on tiberium, harvest; otherwise ring-search outward up to radius 63, randomizing the order of the four sides, and take the richest unoccupied tiberium cell on the first ring that has any (so nearest ring, best density within it). Player harvesters only consider cells the player has uncovered (`UNIT.CPP:2338`). The last harvested cell is remembered as `ArchiveTarget` as a fallback. If nothing is found, it goes to guard and retries after 15 s.
- `Harvesting()` (`UNIT.CPP:2461`): every 1 second (`HarvestTimer = TICKS_PER_SECOND`) it lifts `(OverlayData % 6) + 1` steps, capped by remaining capacity (partial first, then whole six-step "levels"). A rich cell takes two or three scoops. When the cell empties, the overlay is deleted and land type recalculated, then it searches again until full.
- Return: `Find_Best_Refinery` prefers the last-used refinery and otherwise finds the nearest docking bay through the radio-message protocol (`RADIO_HELLO` / roger). The refinery runs its own state machine (`BUILDING.CPP:4467-4540`): dock, siphon, undock. Each siphon tick offloads one step (`Offload_Tiberium_Bail`, `DRIVE.CPP:1641`) worth 25 credits for humans. A refinery grants a free harvester when built (`BUILDING.CPP:2872`).
- Quirk worth knowing: for computer houses in campaign games, a bail returns 708 credits, not 25 (`DRIVE.CPP:1650-1660`; a comment says the formula is wrong but it is kept so campaign missions are not broken). Multiplayer uses a corrected 33 per step (a one-third bonus). So the campaign AI is economically cheating by design or accident.

### Credits, storage and silos
`HouseClass` (`HOUSE.CPP:1717-1850`) has two pools: `Credits` (starting cash, refunds, crate money; uncapped) and `Tiberium` (harvest income; capped by `Capacity`). `Harvested(n)` adds to `Tiberium` and clamps at `Capacity`, setting `IsMaxedOut`: anything over capacity is lost. Capacity is the sum of building `Capacity` values, adjusted on construction, sale, destruction and capture by `Adjust_Capacity`; in TD a refinery stores 1000 (cost 2000) and a silo 1500 (cost 150). If capacity shrinks below stored amount (building sold) the excess is refunded into `Credits`; if destroyed ("inanger") it is lost. `Spend_Money` drains `Tiberium` first, then `Credits`. The sidebar shows `Available_Money = Tiberium + Credits`, counted up/down with a smoothing animation: step is |delta|/32 clamped to 1..143 per update (`CREDITS.CPP:144-171`), which is the "rolling" counter. Silo sprites switch frames by `Tiberium*5/Capacity`. Production deducts money gradually as it builds (not covered here).

### Red Alert differences
- Gold ore and gems are two overlay families (`OVERLAY_GOLD1-4`, `GEMS1-4`) with rules-driven values: `GoldValue=35`, `GemValue=110` (`RULES.CPP:233-235`), `BailCount=28`. Gem cells hold only 3 steps (`_adjgem`), but each scoop adds 4 to the load, so a gem load is roughly 3x the value of a gold load.
- Harvester lifts 1 step per scoop (the %6 logic is commented out), and on arrival it dumps the whole load as a lump via its own animation (`UNIT.CPP:2496-2515`), crediting `Gold*35 + Gems*110` in one go, rather than the TD refinery trickle.
- Growth is rules-driven (`OreGrows`, `OreSpreads`, `GrowthRate` in minutes, default 2). The scan covers the whole map in `GrowthRate` minutes; at the end, every sampled grow candidate gets a step and every spread candidate seeds a neighbour (`MAP.CPP:1022-1110`). Only gold grows or spreads; gems are static (`CELL.CPP:3015-3050`). Spread also requires the germination test (`Can_Tiberium_Germinate`: not a bridge, no building, buildable ground, no overlay).
- Crates (`CRATE.CPP`): one crate tracked at a time, re-rolled after random between 0.5x and 2x `CrateRegen` minutes (default 10), placed on a random buildable cell (water crate with `WaterCrateChance`). Contents are an enum of 18 effects (money, unit, heal base, reveal, darkness, ...). TD's `Goodie_Check` (`CELL.CPP`) has a shorter list (15 kinds).

### AI harvesting
Not a special economy AI. `AI_Unit` (`HOUSE.CPP:6625-6640`) queues a replacement harvester whenever refineries outnumber harvesters (requires IQ >= `IQHarvester` and difficulty not Hard in that branch). The harvesters themselves use the same Mission_Harvest as the player's, plus the 708-credit bug in campaign. `IsTiberiumShort` is checked but I found nothing in TD that ever sets it to true (unverified for RA).

## 4. Shroud and fog

TD has shroud only, no fog of war: once a cell is mapped it stays visible forever. State is one bit pair per cell and, since the Remastered port, per player (`IsMappedByPlayerMask`, `IsVisibleByPlayerMask`, `CELL.H:150-155`). `MapClass::Sight_From(house, cell, range, incremental)` (`MAP.CPP:306`) reveals by walking a precomputed table of offsets sorted by ring (`RadiusOffset`/`RadiusCount`, ranges 1..10, `MAP.CPP:57-72`) and testing `Distance <= sightrange`. Incremental moves only walk the outer two rings. There is no line of sight: terrain does not block vision. Every unit and building calls this as it enters a cell, based on its type's `SightRange`. `DisplayClass::Map_Cell` (`DISPLAY.CPP:1798`) marks the cell, repaints it, then re-checks neighbours because the shroud art only has a fixed set of edge shapes; neighbours are mapped until every pattern is drawable. AI houses are skipped unless `ShareAllyVisibility`, which is why computer players do not need vision to target. RA adds a per-cell `Jammed` counter for the Gap Generator, which re-shrouds an area (`REDALERT/CELL.H:121`).

## 5. The C# map editor (`CnCTDRAMapEditor/`)

**Architecture.** WinForms application, .NET Framework 4.6.2, namespace `MobiusEditor`, depends on Newtonsoft.Json, Pfim (image decoding) and a bundled Steamworks.NET. Of 54.7k lines, roughly 17k are generated Steamworks bindings and 6k a TGA library; the editor proper is about 20k. Layers:

- `Program.cs`: loads the game's `DATA\*.MEG` archives (CONFIG, TEXTURES_*), then builds `TextureManager`, `TilesetManager` (tilesets described by XML in the megafile), team colour and game-text managers; initializes Steam if this is a Steam build.
- `Interface/IGamePlugin`: `New`, `Load(path, fileType)`, `Save`. Two implementations, `TiberianDawn/GamePlugin.cs` (1344 lines) and `RedAlert/GamePlugin.cs` (1773). Each owns the type lists (`TemplateTypes.cs`, `OverlayTypes.cs`, `UnitTypes.cs`, ...) and all INI mapping. This is the right seam for a data-driven editor.
- `Model/`: `Map` aggregates `CellGrid<Template>`, `CellGrid<Overlay>`, `CellGrid<Smudge>`, occupier sets for technos/buildings, 28 `Waypoint`s, cell triggers, `Triggers`, `TeamTypes`, `Houses`, and the INI sections as property-change-notifying classes. `Map` batches updates and invalidates by `MapLayerFlag` plus point sets. `TotalResources` sums (icon+1)*value over overlays, giving mapmakers a live economy number.
- `Render/MapRenderer.cs` (835 lines): static GDI+ rendering, layer-masked and clipped to invalidated cells; `Controls/MapPanel` hosts it with zoom; `Widgets/NavigationWidget` draws cell cursors.
- `Tools/`: one class per tool, all derived from `ViewTool` and `ITool`: Template (picks a template and stamps its W x H footprint, with Shift/Ctrl modes and a bounds mode that drags the playable rectangle), Resources (brush-size paint of tiberium/gems, density derived), Overlays, Walls, Smudge, Terrain, Units, Infantry, Buildings, Waypoints, CellTriggers. Dialogs edit Triggers, TeamTypes and map settings.
- `Utility/UndoRedoList<T>`: closure-based undo (each tool registers an undo lambda and a redo lambda). `INI.cs` is a hand-rolled INI parser with section diffing. `WWCompression.cs` implements Westwood LCW. `Megafile*.cs` read/write the Petroglyph MEG container.

**Editing workflow.** New map (pick theater and size, 64 max for TD, 128 for RA) → paint terrain templates → set playable bounds → paint resources → place walls/overlays/terrain objects → place units, infantry, buildings per house → set waypoints (P0-P7 for multiplayer, Home for single-player) → define teams and triggers → map settings (briefing, basic, per-house) → Save. Save runs `Validate()` against hard limits (100 aircraft, 500 structures/infantry/terrain/units, 60 team types, 80 triggers, at least 2 player-start waypoints for skirmish, a Home waypoint for single-player; `TiberianDawn/Constants.cs:25-33`).

**Serialization.** Load reads `.INI` then `.BIN` (or both from a MEG). Save writes five artefacts: INI, BIN, a TGA preview, a JSON metadata file (map rectangle, theater, start waypoints) for the Remastered UI, and optionally a `.MEG`/`.PGM` bundle for the Workshop. Unknown INI sections survive round trips (`extraSections`).

**Steam coupling.** `SteamworksUGC.cs` implements Workshop create/update through `CreateItem`/`SubmitItemUpdate`; `SteamSection` in the INI stores title, description, preview and `PublishedFileId`. Menus hide Publish when not a Steam build. The author name comes from `SteamFriends.GetPersonaName`. This is removable, being self-contained.

**Portability as our base.** Positives: GPL, small model layer, plugin split, undo, validation, WinForms is fine for a Windows-only project, and the output format is the C&C one we may adopt. Negatives: (1) it will not start without the Remastered `DATA\*.MEG` textures (EA assets we cannot ship or depend on; would have to replace TextureManager/TilesetManager with our own art); (2) type lists (units, buildings, houses, triggers) are hard-coded C# tables mirroring the C++ enums, so a new game's content needs code changes; (3) .NET Framework 4.6.2 and GDI+ rendering are dated (retargeting to .NET 8 WinForms is plausible but untested); (4) the editor and the game are separate codebases sharing only a file format, so any rule change is duplicated. If our game is C#, the model and tools are a reasonable template to rewrite against our own data tables. If our game is not C#, there is no code to share.

## 6. Design principles visible in the data

No map files are in the repo, so this is inferred from structure and limits, not measured. TD maps are 64x64 with a 62x62 default window and caps of 500 units, 80 triggers and 60 teams, so campaign maps were small, hand-scripted spaces (RA's 128x128 is four times the area). Eight start waypoints (0-7) is the multiplayer maximum; skirmish needs two. Fields per start cannot be counted here, but the mechanics show that tiberium regrows only from density-7+ cells or blossom trees, and that harvesters path to the nearest ring with any tiberium, so field placement relative to the refinery sets income. Choke points come purely from template choice: rock and water are 0x00 for every ground class, and bridge and ford templates reopen specific cells.

## Implications for RTS_2027

- **Map format.** Keep the C&C idea of "readable text for entities, dense binary for terrain", but do not copy the exact files. Terrain as a 2-bytes-per-cell blob is compact and trivially diffable only by tools; entities as INI lines are easy for a hobbyist to hand edit and diff in git. **Recommendation:** one text file per mission (JSON or TOML with a schema version, entities and triggers referenced by string id) and the terrain layers as a sibling binary or PNG-like grid (or an embedded base64 block), plus a hash for LAN sync. JSON beats INI because teams and triggers have nested lists.
- **Tiled TMX.** TMX handles tile layers and object layers and the Tiled editor is free, but it knows nothing about C&C-style multi-cell templates with holes, per-icon land-type exceptions, waypoints with special roles, or trigger/team dialogs. Using it means writing a custom exporter plus custom-property conventions, and the trigger/team authoring UX would still need our own tool.
- **Tile approach.** Use C&C's template model (a template is a named W x H stamp with a per-cell hole mask and per-cell terrain class) rather than per-cell free painting. It gives artists organic shapes and lets us compute passability and buildability from the same data. Store, per cell, the template id + sub-icon (so the editor can re-stamp), and cache derived land type at load. Trade-off: more authoring work for the tileset (every template needs hole map and class exceptions), but better-looking maps and easy water/cliff choke points.
- **Land type as a data table.** Copy `Ground[]`: terrain class x locomotion class -> speed multiplier (0 = blocked), plus a buildable flag. It lives in a data file so units and mods can add classes without code.
- **Map size.** Support up to 128x128 (RA scale) in the format, but target 64x64-class missions at first. Full-map scans like the tiberium sweep are cheap at these sizes.
- **Resource model.** Store density per cell (a small integer) and derive value from it; show a few visual variants independent of density. **Recommendation:** use the TD-style slow sweep with candidate lists (local, deterministic with the sim's seeded RNG, trivially cheap) but take RA's idea of making rates data-driven (`GrowthRate`, `Spreads`, `Grows`) and of restricting growth to certain resource types. Make "no regrowth" a legal mission setting for scarcity. Include a seed object (like the blossom tree) so designers can choose where fields regenerate.
- **Harvest and income.** Choose between TD trickle (refinery siphons bail by bail, which looks good and makes dock time a balance lever) and RA lump (simpler state machine). **Recommendation:** trickle unload, but keep the pool split: a capped storage pool plus an uncapped cash pool. Capped storage with overflow loss is the lever that makes silos a decision. Don't copy the 708-per-bail AI bug; expose an explicit per-difficulty harvest multiplier instead.
- **Harvester AI.** The ring search with "richest cell on nearest ring" and "remember last field" is a small, adequate baseline and worth copying. For better play add field reservation (avoid all harvesters picking the same cell) and danger avoidance.
- **Shroud.** Per-player bit masks with a precomputed offset-ring reveal are simple and fast. Decide first whether we want RA/TD permanent shroud or true fog; true fog needs a per-frame visible mask and a "last seen" snapshot for buildings.
- **Editor choice.** **Recommendation:** write our own editor, in the same language/engine as the game so it shares the sim's types and data tables, and borrow the design (plugin seam, layered `Map` model, layer-flag invalidation, closure undo, save-time validation with caps). Do not fork the EA editor: it needs EA's textures, its type tables are hard-coded, and removing Steam and MEG dependencies would be most of the work. Do use it as a feature checklist. Tiled is reasonable only as a stopgap for terrain prototyping before our editor exists.
- **Keep scripts out of code.** The TD loader has per-mission hard-coded fixes. Put every mission quirk in the map data (trigger actions, per-cell land overrides) so it is editable.

## Open questions for the owner

1. **Engine/language** (decided elsewhere): is the game C#? If yes, a WinForms or in-engine editor sharing the game's classes is much cheaper; if not, which language for the editor? Options: same as game, C# WinForms separate, or a Tiled plugin + converter.
2. **Resource regeneration:** do you want a self-renewing economy (TD/RA style, rewards defending and expanding) or fixed finite fields (rewards early aggression and map control)? Or a per-map switch?
3. **Income feel:** trickle unload at the refinery, lump sum, or per-bail credit pop-ups as the harvester drops? This changes harvester AI, refinery design and balance.
4. **Fog:** classic permanent shroud, shroud plus fog of war, or reveal-all in skirmish?
5. **Map editor scope:** is a visual editor a goal for a hobby project, or is hand-edited text plus a terrain painting tool enough at first? Will you want to ship user-made maps?
6. **Theaters:** how many terrain sets do you want for the campaign (C&C had 3-4)? Each one multiplies art cost, since every template needs a variant per theater.
