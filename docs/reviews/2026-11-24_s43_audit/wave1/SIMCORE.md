## Findings

### SIMCORE-01 · MED · bug
What: `CanPlace` bounds test `x0 + w > Width` overflows for a huge top-left X (or Y), so the OutOfMap guard is skipped and the footprint scan indexes the map array out of range -> IndexOutOfRangeException inside `Step`.
Where: src/Sim/Simulation.cs:479 (`if (x0 < 0 || y0 < 0 || x0 + w > Setup.Map.Width || y0 + h > Setup.Map.Height) return PlacementResult.OutOfMap;`), reached with the raw command cell from ApplyPlace (src/Sim/Simulation.Production.cs:206-213, no `InMap(c.Cell)` check unlike Move/Rally/Harvest/Pack). Crash site: `CheckBeachheadAndWater` -> `_map.LandAt(c)` = `_land[c.Y * Width + c.X]` (src/Sim/Map/MapState.cs:55-57, no bounds check).
Evidence: read — no `<CheckForOverflowUnderflow>` anywhere (grep of *.csproj/*.props), so int math is unchecked: Cell.X = 2147483647 with footprint w >= 1 gives x0 + w = int.MinValue, which is not > Width. Net layer does not range-check cells: NetCodec.Commands() (src/Net/NetCodec.cs:322-338) copies `new CellCoord(I32(), I32())` verbatim and TurnScheduler.Submit only checks `command.Player == slot`. Precondition for the attacker: a finished structure waiting in the lane (`_production.Ready[lane] == c.Arg`), which any guest gets by building one cheap structure. Not run (no .NET SDK).
Impact: A modified LAN client can crash every peer deterministically on the same tick (the exception is thrown on all peers). Same shape is reachable from a hand-edited replay (ReplayReader accepts any int cell). No effect in normal play.
Fix idea: Use `topLeft.X > Width - w` style checks (or `long` math / `Setup.Map.Contains` on both corners) in CanPlace and UnpackSiteOk (Rigs.cs:73 has the same pattern but is guarded by `InMap(c.Cell)` today), and add an `InMap(c.Cell)` guard in ApplyPlace.   Changes a match outcome / number / visible text?: no

### SIMCORE-02 · LOW · debt
What: Save and replay format numbers were not bumped when new built-in state parts were appended after format 13 (Nov 7): "commander_orders" (Nov 13, commit fd79e108) and "props" (Nov 16, commit 55d7e04a). A save or replay written by a build between Nov 7 and Nov 16 still claims format 13 but has a different part list; it is accepted by the header check and then fails late.
Where: src/Sim/Serialization/SimWriter.cs:22 (`SaveVersion = 13`), src/Sim/Replay/ReplayWriter.cs:21-25 (`Version = 13`, `OldestReadableVersion = 7`), part list at src/Sim/Simulation.cs:118-139.
Evidence: script — `git log -S'"props"' -- src/Sim` -> 55d7e04a 2026-11-16; `git log -S'commander_orders'` -> fd79e108 2026-11-13; `git log -L` on SaveVersion shows last bump c7a99234 2026-11-07. Part names are written into the full hash (Simulation.Hashing.cs:79-80), so an older v13 replay mismatches at its first hash record and FirstDifferentPart names the first part present in only one list ("commander_orders"), i.e. a false "desync". An older v13 save fails in SimReader.ReadState with EndOfStreamException, which Simulation.FinishLoad turns into "Truncated save." (misleading). Same applies to replays v7..v12: the reader accepts them (OldestReadableVersion = 7) but they can never verify because the part list differs (comment in ReplayReader says "Replays from other versions cannot be played back").
Impact: Owner-side only: an old replay or save from before Nov 16 reports a desync or a damaged file instead of "recorded by an older build". The embedded-rules load path (Simulation.Load with rulesFromBlob) skips the rules-hash guard that would normally catch this.
Fix idea: Bump SaveVersion/ReplayWriter.Version for each part added, and raise OldestReadableVersion to the first version whose hashes this build can reproduce.   Changes a match outcome / number / visible text?: no (error text only)

### SIMCORE-03 · LOW · ux
What: `ClearQueueForPlainOrder` runs before the order is validated, so a refused plain order wipes the unit's shift-queued waypoints and still leaves it on its old mission.
Where: src/Sim/Simulation.cs:327 (call) and src/Sim/Simulation.Orders.cs:79-87. It only checks that the subject is alive and owned, not that the order will be accepted (Move to an off-map cell breaks out at Simulation.cs:333; Attack with a dead/untargetable target returns at Simulation.Combat.cs:445; MoveGoalRefused at Simulation.Movement.cs:38).
Evidence: read.
Impact: A player with a 5-waypoint queue who right-clicks a target that died a moment earlier (or on an unreachable water goal, M7-03) loses the whole queue and the order does nothing.
Fix idea: Clear the queue from inside the handlers on the success path (or have handlers return bool), keep SetStance/QueueOrder as they are.   Changes a match outcome / number / visible text?: yes (queue survives a refused order)

### SIMCORE-04 · LOW · qol
What: Saves carry no integrity check: no trailing state hash and no end marker, and `Tick` is taken as read. A save with a flipped bit inside a numeric field (not a length or name) loads silently into a diverged or odd state.
Where: src/Sim/Serialization/SimWriter.cs:25-40 (WriteState has no hash/marker), src/Sim/Serialization/SimReader.cs:25-37, src/Sim/Simulation.cs:914-924 (FinishLoad sets `Tick = state.Tick` unchecked; `_recentHashes` is empty after load).
Evidence: read.
Impact: Disk corruption or a half-copied save is not reported; the LAN resync path (LanSession.cs:643 Simulation.Load) cannot cross-check the loaded sim against the sender's hash inside the sim layer.
Fix idea: Append `ComputeStateHash()` at the end of a save and compare after FinishLoad; reject negative Tick.   Changes a match outcome / number / visible text?: no

## Suspects (unproven)
- Stale `_open` cache after Load: `SealsRegion` caches `_open` keyed only on `_map.Version` (src/Sim/Simulation.cs:507-513) and `_openVersion` starts at -1, but extension `OnSetup` runs before Load (src/Sim/Simulation.cs:141) and can call `CanPlace`. MapState.Read then restores the saved `Version` (Map/MapState.cs:170). If the saved Version equals the Version at the last pre-load CanPlace, the loaded sim reuses an `_open` grid from the unloaded map and CanPlace's gap rule gives a different answer than a continuous run. Needs: a mission with setup-time CanPlace calls, and a save whose map Version collides. Proof would be a test: build sim, call CanPlace in OnSetup, Save at a tick whose Version matches, Load, compare CanPlace to the original. Probably rare (Version is large by the time a game is saved). Same pattern in Pathing RegionCache (guarded by the `_epoch++` in PathService.Read, so likely fine).
- Carried-unit order filter is narrower than the carried-unit rule: `IsOrderToCarriedUnit` (src/Sim/Simulation.cs:379-385) lists Move/Stop/Scatter/Attack/AttackMove/Guard/Enter/AttackGround/QueueOrder but not Harvest, Return, Deploy, Pack or SetStance. A harvester carried as a vehicle passenger (vehicle_slots = 2 in data/rules/vehicles.toml:765) could take a Harvest/Return order; ParkVehiclePassenger resets it each tick (Simulation.VehiclePassengers.cs:79-88) but SyncPassengers runs after RunMissions, so the mission handler gets one tick of side effects (economy Touch/HomeRefinery set by Return, path request). Proof: a test that boards a harvester on a landing craft, sends Return with Target = own refinery, and compares economy state before/after one tick.
- Command Arg decoding is inconsistent: Move/Stop/Scatter use the whole `c.Arg` as the subject kind (Simulation.Movement.cs:36, `OwnsSubject`), while IsOrderToCarriedUnit/ClearQueueForPlainOrder and the combat commands use `c.Arg & 0xFF`. A Move with Arg = 0x100 is judged "vehicle" by the carried-unit check but rejected by OwnsSubject. Harmless today (the stricter reading wins), but a trap for the next command kind.
- Build/Place do not check `type.Faction` against the player's faction; the only gate is prerequisites (CanResearch does check faction). Script check on data/rules (142 buildable types in vehicles/infantry/buildings.toml): every one has at least one prerequisite provided by a same-prefix (own-faction) building, so no cross-faction build is possible without capturing an enemy building. If a future type is added with empty or shared prerequisites, a crafted Build command would bypass the UI faction filter.

## Checked and fine
- Determinism greps over all of src/Sim: no float/double/decimal, no Math.Sqrt/Sin/Cos/Pow, no System.Random, DateTime, Stopwatch, Guid, string.GetHashCode, HashSet, LINQ, Parallel/Thread/lock; no mutable static fields (only readonly tables and the RulesDeriver ConditionalWeakTable memo, keyed lookup only).
- Dictionary use in Sim: PathService `_cache` is lookup-only (CacheValue stores Expansions, so a loaded sim with an empty cache pays the same budget); `_results` is a SortedDictionary and written in key order. The only List.Sort with a comparator (Simulation.Shipments.cs:274) has a total order (D, T with T = +-k, unique per k).
- State coverage: scripted cross-check of every `ISimStatePart` implementation (25 files) — every array/list/scalar field is referenced in its Write path or is a derived/capacity field (HasFree, VehicleCapacity, MaxQueue, Capacity, Width/Height/PlayerCount); StatsState writes through `All`. Slot-reuse check: per-slot arrays of Tunnels/Veterancy/Naval/Rigs/Salvage/Economy/Combat are reset by their Clear*/ResetOrders hooks, and OnActorRemoving -> OnCombatActorRemoving -> ResetOrders covers every removal path (RunCleanup, RemoveMobileQuietly, RemoveBuilding).
- Derived-not-saved fields are rebuilt after Load: `_emittersDirty`, `SupplyChanged()` (FinishLoad), `_teamMembers` (teams immutable), `_regrowth`, `_lifeline*`, `_groutingBits`, `_hard*` scratch, `_pendingMoves`/`_pendingDamage` (drained within the tick), `_fx`/`_killers` (cleared at StepCore start). Hardened/HardeningDirty/GroutedPlayers are saved in the ground part.
- New since Nov 12: EconomyState version 6 (HomeRefinery, IdleSince) written/read/cleared/IsDirty consistently; MobileStore stuck-clock arrays are saved and hashed only while `StuckClock` is set, and the flag comes from rules embedded in the header; PropState writes sparse (index, health) and validates index; CommanderOrderState/Directive Unpack/Clamp reject bad kind/slot (bits cannot index out of range; amount 24-bit unpacked via uint).
- Numerics: Fixed32 is not referenced anywhere in src/Sim (dead but harmless); Facing tables are 256/257 entries (FromDelta ratio max 256 stays in range); LeptonMath uses long for DistanceSquared and ISqrt is exact; max map 128 cells = 32768 leptons, so lepton math cannot overflow int. SimRandom.Next only throws for maxExclusive <= 0 and its three call sites pass constants or `2*r+1` from rules (r < 0 would be a data error).
- Command validation, all verified to check alive + owner (+ kind bits) before touching arrays: Move/Stop/Scatter/Attack*/Guard/SetStance/QueueOrder (OwnsSubject, InMap), Build/Cancel/Hold (category range, TryTypeInfo bounds, queue bounds, Arg2 < 0 rejected except the -1 ready-cancel), Sell/Repair/Rally, Harvest/Return (IsRefineryOf), Enter/Deploy/Unload/Pack/Upgrade (type index range), Special (CanFireSuperweapon: owner, charge, `_ground.Contains`), Directive/CommanderOrder (neutral and range checks, cell InMap + explored). SlotArray.IsAlive bounds-checks Index (ushort up to 65535 against Capacity <= 65535). Debug ops and the free Place are gated by `Setup.AllowDebug`, which is false for skirmish setups (SkirmishGame.cs:166,281) and is part of the save/replay header.
- Net binding: TurnScheduler.Submit rejects a command whose Player is not the peer's slot, with per-player and per-tick caps (MaxCommandsPerPlayerPerTick 64, MaxCommandsPerTick 1024), so ApplyInput's O(n^2) insertion sort is bounded.
- Replay: spawn records are always stamped tick 0 in practice (RequireSetupPhase forbids setup calls after tick 0 outside Step), hook-based setup is cross-checked against recorded spawns, truncated files are read to the last complete record, RulesBlob caps decompressed size at 64 MiB and file count at 4096, mission id length is capped.
- Header: CheckMatches covers rules hash, map hash, seed (replay), size, players, teams, limits, AllowDebug, NoRebuildDefeat, handicap, starting cash, factions; limits are range-checked (<= 1<<20 in the header, <= 65535 in SlotArray, so a crafted header cannot wrap ushort ids). Handicap 10..200 fits the byte written to the header. `LandingMarkers` is deliberately not in the header (AI-only, sim never reads it).
