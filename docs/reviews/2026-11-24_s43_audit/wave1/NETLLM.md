# NETLLM — LAN multiplayer and LLM provider code (security and robustness)
Scope read: src/Net/ (all: NetCodec, NetMessage, NetProtocol, INetTransport, Udp/UdpTransport, Udp/ReliableChannel, Lockstep/*, Discovery/*; Loopback only skimmed), src/Game/Lan/ (all: LanSession, LanResync, LanTransportTap, LanDesyncReport, ContentHash, LanMatch, LanMatchSetup, LanChatInput; LanOverlay/LanText/LanMenuScreen not read), src/Game/Lan/Lobby/ (LobbyHost, LobbyClient, LobbyCodec, SetupCodec, SlotChange, BlobReader/Writer, MapReceiver, MapChunker, LobbyMap, LobbyData, LobbyNames, LanAddress), src/Llm/ (ProviderHttp, both providers, KeyPolicy, ProviderKeyring, DpapiSecretStore, Commander, ReplyParser, CommanderPrompt, DirectiveCommands, ProviderDefaults, PersonaCatalog, Contracts, CommanderContracts; BattlefieldSummary/SummaryHistory only grepped), data/llm/*.toml. Also read for context: Game/Sandbox/CommanderSet.cs, Game/Screens/LobbyScreen.cs (Exit/Update/BeginMatch), LanBrowserScreen.HostGame, Sim Apply/ApplyDebug/ApplyDirective, Data/MapFile.cs size checks.
The LAN and LLM code has had no change since the session-18 audit except two lobby-codec lines (handicap, stamps); the s18 audit did not cover LAN. Still broken from s18: nothing found in this scope (the s18 key-per-provider and http-key rules are in place: KeyPolicy.cs, ProviderKeyring.cs).

## Findings

### NETLLM-01 · MED · bug
What: The join check (`ContentHash`) leaves out `data/stamps/`, but generated LAN maps are built on each peer from the lobby parameters plus the local stamp files (the lobby carries a `Stamps` switch, M12-13b). Two installs with different stamp files pass the Hello check and then build different maps.
Where: src/Game/Lan/ContentHash.cs:14 (`Folders = { "rules", "ai", "mapgen", "maps", "missions", "campaigns", "theaters" }`); src/Data/Stamps/StampLibrary.cs:39-44 (loads `data/stamps/*.toml`); src/Game/Lan/Lobby/LobbyCodec.cs (WriteMap writes `g.Stamps`).
Evidence: script — `ls data/stamps` gives bridge, checkpoint, crater_field, grove, ruined_block (5 .toml). None of the 7 hashed folders contains them. The class comment promises "every data file the simulation or the mission scripts read" and "two installs with different gameplay data refuse each other at join time".
Impact: A modded or half-updated install (same BuildVersion, edited stamp toml) joins, the match starts, and the map differs from tick 0. Result is an immediate hash desync (or a start with unrelated terrain) instead of a clear "Game data differs" refusal at the lobby.
Fix idea: add "stamps" to `Folders` (and re-pin any test that pins the hash value).   Changes a match outcome / number / visible text?: no (the hash value changes, so old and new builds refuse each other; same BuildVersion bump applies).

### NETLLM-02 · MED · bug
What: A client can wedge the host's tick loop with one unreliable `Progress` message. The host stores `SteppedTick` if it is larger than the old value and checks `tick > stepped + MaxLead` in 32-bit signed arithmetic. `SteppedTick = int.MaxValue` makes `stepped + MaxLead` wrap negative, so the peer counts as blocking for ever.
Where: src/Net/Lockstep/LockstepHost.cs Handle `case NetMessage.Progress` (accepts any larger int, no upper bound); `IsBlocked` and `UpdateWaiting` (`tick > stepped + MaxLead`). NetCodec.Decode accepts any I32.
Evidence: script — int32 wrap check: (2147483647 + 8) as int32 = -2147483641, so `tick > -2147483641` is true for every tick. Read: `_progress` can only increase, so the value cannot be corrected.
Impact: One hostile or buggy guest freezes everyone: the waiting overlay shows from 1 s, the host may drop after 10 s, and the host auto-drops it after 60 s (`AutoDropMs`). Not a crash, but a griefing stall of 10-60 s that a bad client can trigger in the first second of a match. The opposite value (a huge but non-wrapping number, e.g. 1,000,000) hides the peer's real lag: the host never waits for it again and runs more than MaxLead ahead.
Fix idea: clamp `SteppedTick` to `<= Tick` (a client cannot have stepped past the host's sealed ticks, `SealedThrough + 1`) and use long arithmetic in IsBlocked/UpdateWaiting.   Changes a match outcome / number / visible text?: no

### NETLLM-03 · MED · bug
What: Peer ids are never reused or wrapped (`_nextPeer++` on every accepted join) but both lobby codecs reject any peer id above 1000. After 1000 accepted joins in one hosted lobby, `LobbyState` fails to decode on every client ("The host sent a lobby this version does not understand") and clients leave; the lobby is dead for everyone.
Where: src/Game/Lan/Lobby/LobbyHost.cs HandleHello (`id = _nextPeer++`, also burned when `Accept` fails); src/Game/Lan/Lobby/LobbyCodec.cs Decode (`peer > 1000`, both slots and spectators); SetupCodec.cs (`peer > 1000`).
Evidence: read. A guest that joins and leaves in a loop (or a flaky client whose Bye is lost and that reconnects from new source ports) spends one id per cycle; nothing recycles ids.
Impact: Normally unreachable at home (1000 joins), but one hostile or looping guest can brick a lobby on purpose, and a lobby left open all day with rejoining kids drifts toward it. Failure mode is confusing (everyone told the version is wrong).
Fix idea: reuse the lowest free id above 0, and do not spend an id when Accept fails.   Changes a match outcome / number / visible text?: no

### NETLLM-04 · MED · bug
What: A commander reply that arrives more than 600 ticks (30 s of game time) after its request is silently thrown away as "stale", yet the settings allow `timeout_seconds` up to 600 and the providers.toml comment tells players to raise it for a slow local CPU model.
Where: src/Llm/Commander.cs Handle (`if (tick - _requestTick > CadenceTicks) return false;   // stale`); src/Llm/ProviderDefaults.cs Seconds (5..600) and the `timeout_seconds` doc; data/llm/providers.toml last comment line.
Evidence: read. Next call is only started after the previous one is taken (`_inFlight`), so a model that needs 40 s gets a call, 40 s of waiting, a discarded reply, then a new call. No chat line is posted (Online stays true; the offline and cap notices only fire on failure or cap), and every discarded call counts against `LlmCallCap`.
Impact: Players who follow the advice and raise the timeout for a local model get a commander that never acts and never says why, while spending calls. Hosted models inside 30 s are unaffected.
Fix idea: measure staleness in game time relative to the reply, but accept replies up to the timeout (or post a "reply arrived too late" line and lengthen the cadence).   Changes a match outcome / number / visible text?: yes (commander directives would start to apply for slow models).

### NETLLM-05 · MED · perf
What: There is no cap on the model reply size, and `ReplyParser.Parse` is quadratic on a reply with many `{`. It runs on the game thread inside `Commander.Poll`, which is inside the host's tick loop in LAN.
Where: src/Llm/ProviderHttp.cs SendAsync (`ReadAsStringAsync` reads the whole body; only the 20 s timeout limits it); src/Llm/ReplyParser.cs Parse (for each `{` it calls `MatchEnd`, which scans to the end of the string; when no match is found it moves on by one character).
Evidence: script — operation count for "{" x n: n=5,000: 12.5 million (fine); n=200,000: 2.0e10; n=2,000,000: 2.0e12 character steps. Read: a normal 1,200-token reply is about 5 KB and is harmless; max_tokens is sent to the server but a non-compliant OpenAI-compatible server may ignore it.
Impact: A local server that ignores max_tokens, or a runaway generation, can freeze the host's game loop for seconds to minutes. In LAN that stops sealing bundles, the waiting overlay appears for all clients, and after 60 s of host silence clients time out (HostLost). Single-player: the game freezes.
Fix idea: cap the body (e.g. 64 KB via a limited read) and the text passed to the parser (e.g. 16 KB), and stop scanning after the first unmatched `{`.   Changes a match outcome / number / visible text?: no

### NETLLM-06 · MED · bug
What: A peer that the host's transport drops for silence (60 s), a protocol violation or a malformed message is removed without any message to it, and its later packets create a new pending peer that the host keeps alive with acks and keepalives. The client never learns it was dropped: no `PeerDropped` (the broadcast excludes it, it is no longer in `_connected`), no `Bye`, no timeout.
Where: src/Net/Udp/UdpTransport.cs Drop (removes from `_connected`, no Bye), Poll (`Faulted` -> "protocol violation", timeout), DrainMessages (malformed -> `Drop(peer, "malformed message")`), ReceiveAll (unknown endpoint on the host becomes a pending peer when `OnPacket` accepts it, `Started = true`, then `Flush` answers it); src/Net/Lockstep/LockstepHost.cs Update (event -> `Drop` -> `Broadcast` after the peer is already gone).
Evidence: read. The zombie's packets are valid datagrams (magic byte, header), `OnPacket` returns true, the host's `Flush` sends keepalives every 250 ms, and `LastReceivedMicros` keeps being refreshed on both sides, so neither side times out. Its reliable units have sequence numbers > 0, so they sit in `_recvBuf` and are never delivered; they are acked at packet level, so the client thinks they arrived.
Impact: Laptop sleep, Wi-Fi roam or a long stall (> 60 s) during a match: the host drops the player and an AI takes the slot, but that player's screen just freezes with no notice, no "you were dropped" line and no "Continue against AI" offer (that needs HostLost). In the lobby, a kicked client whose single best-effort Bye datagram was lost stays in a stale lobby view. Each zombie also holds one of the 16 pending slots (see NETLLM-07).
Fix idea: when a connected peer is dropped for a reason other than its own Bye, send one best-effort Bye, and have the host answer a non-Hello packet from an unknown endpoint with a Bye or ignore it.   Changes a match outcome / number / visible text?: no (adds a notice).

### NETLLM-07 · LOW · bug
What: The host accepts at most 16 pending (not yet Hello'd) peers, creates one for any datagram that starts with the magic byte 0x52, and silently ignores further new endpoints. Pending peers never expire while they keep sending.
Where: src/Net/Udp/UdpTransport.cs MaxPending = 16, ReceiveAll (`_peers.Count(x => x.Pending) >= MaxPending` then `continue`, no Reject), Poll (timeout only after 60 s of silence).
Evidence: read.
Impact: Anyone on the LAN (or a few zombie sessions from NETLLM-06) can fill the 16 slots with one tiny packet each from 16 source ports and keep them filled; real joiners then see no answer at all and sit in "Connecting" for the 60 s timeout. Same for a spoofed-source flood, which also makes the host send an ack and keepalives to each spoofed address.
Fix idea: expire a pending peer that has not produced a Hello within a few seconds, and send a Reject ("host busy") when the table is full.   Changes a match outcome / number / visible text?: no

### NETLLM-08 · LOW · ux
What: A Hello that reaches the host after the match started is never answered. The lobby (which would send "The game has already started.") is no longer polling; the lockstep host receives the surfaced Hello and ignores it.
Where: src/Net/Lockstep/LockstepHost.cs Handle (no case for Hello); src/Game/Lan/Lobby/LobbyHost.cs Handshake (`_started` text exists but only runs while the lobby polls); LobbyScreen.Update is not running under the match screen, so the discovery responder is not polled either.
Evidence: read.
Impact: Someone joining by IP just after the host pressed Start waits the full 60 s and then sees "Could not reach the host".
Fix idea: in LockstepHost, answer a pending Hello with `Reject("The game has already started.")` (needs the transport's Reject path, as the lobby does).   Changes a match outcome / number / visible text?: no

### NETLLM-09 · LOW · bug
What: The discovery responder answers any probe from any source address, with a reply about 6 times larger than the probe, and the reply carries the host's player name (default: the Windows user name) and lobby counts.
Where: src/Net/Discovery/DiscoveryResponder.cs Poll (`_socket.SendTo(reply, from)` with no source check; socket bound to `IPAddress.Any`); DiscoveryPacket.EncodeProbe about 13 bytes vs EncodeReply about 4+1+8+4+1+name(up to 64)+5 bytes; src/Game/Screens/LanBrowserScreen.cs HostGame (name = `PlayerName`); design 20 §8 item 4 (name defaults to the Windows user name).
Evidence: read. The probe side is local-only (multicast TTL 1, directed broadcasts), but the responder never checks that the sender is on a local subnet.
Impact: Only matters if UDP 47271 is reachable from outside the LAN (port forward, a host with a public address, Windows firewall rule for "Public" networks): then anyone can learn the user name and use the host as a small UDP reflector. On a normal home network this is a LAN-only disclosure of a login name by design.
Fix idea: ignore probes whose source is not in a local interface's subnet (or is not private/link-local), and only answer while the lobby is open.   Changes a match outcome / number / visible text?: no

### NETLLM-10 · LOW · qol
What: Each "Continue" after a desync lets play resume on diverged sims, so the next hash check (16 ticks later) reports again, pauses again and writes another desync report folder with a full save and a replay copy. Nothing prunes or limits these folders.
Where: src/Game/Lan/LanSession.cs OnDesync (writes a report per desync), ContinueAfterDesync; src/Net/Lockstep/LockstepHost.cs ContinueAfterDesync (`_desyncOpen = false`); src/Game/Lan/LanDesyncReport.cs Write (new folder per call, no cap).
Evidence: read.
Impact: A group that keeps pressing Continue gets a pause every few seconds and a few MB per cycle under %APPDATA%/RTS_2027/desync, on host and clients. Only Resync fixes the divergence; the dialog does not say Continue is not sustainable.
Fix idea: keep at most N report folders, and after a second desync within a minute offer only Resync / End.   Changes a match outcome / number / visible text?: yes (dialog wording or options)

## Suspects (unproven)
- Redirects and the Anthropic key: `ProviderHttp.MakeClient` uses a default `HttpClient`, which follows redirects. `Authorization` (OpenAI path) is cleared by .NET on redirect, but `x-api-key` (Anthropic path) is a custom header and may be re-sent to a redirect target on another host (https to https, or http loopback to http remote). Needs a test with a handler that returns 307 to prove it. Only matters when the configured base URL is not a trusted server.
- Remote chat text: `LockstepHost.Relay` and `LobbyHost.Say` trim and cut to 200 chars but do not strip control characters or newlines (only the local `LanChatInput` filters to ASCII). A modified client could send `\n` or other control characters. BitmapFont maps unknown glyphs to '?', so probably cosmetic; would need a look at how LanOverlay/lobby draw a line with `\n`.
- `KeyPolicy.IsLoopbackHost` treats any `*.localhost` host as loopback. Windows does not resolve arbitrary `x.localhost` names to 127.0.0.1 in all builds; if it resolved elsewhere (hosts file, split DNS), a key could go over plain http to that name. Needs a real resolver check.
- `LanResync.Assemble` inflates with no size limit and `ApplyResync` catches only some exception types (a `KeyNotFoundException` from a chunk set with changing `Count` would escape). Host-sourced only, so a trust-the-host issue, not an attack from a guest.
- No packet authentication or encryption: a datagram is accepted by source IP:port plus a 1-byte magic and packet ids. Anyone on the LAN who can guess or observe a peer's port can inject or reset a session. This is the LAN-only design (D-005); noting it so nobody assumes more.
- `TurnScheduler` sequence is a `ushort`; once per 65,536 commands of one player a wrap inside a single tick reorders that player's commands in that bundle. It is deterministic on all peers (everyone sorts the same way), so no desync, just a one-in-65k ordering glitch.

## Checked and fine
- NetCodec.Decode: every count and length is checked against the bytes actually present before allocating (Blob up to 256 KB, Commands <= 4096 x 32 bytes, IntList <= 64, SubHashes <= 64, strings <= 512 bytes); trailing bytes, bad bools, bad UTF-8, unknown tags and bad chunk indices all become InvalidDataException; one malformed message drops the peer (no crash, no hang).
- ReliableChannel: whole datagram validated before any state changes; fragment reassembly capped at 512 KB then `Faulted`; receive window 512, send window 256, unreliable queue 256; ack bit maths for id wrap looked right; per-poll receive cap 1024 and per-peer send cap 16 so the loop cannot spin; the WSAEMSGSIZE and ICMP-reset cases are caught and bounded.
- TurnScheduler: a peer can only submit for its own slot (`command.Player != slot` rejected), ExecTick and Sequence are restamped by the host, per-player pending cap 1024, per-tick caps with deterministic spill; spectators and dropped peers have no slot. Sim Apply additionally checks entity ownership (`OwnsSubject` seen on Move/Stop/Scatter) and ignores Debug (AllowDebug is false for networked games, SkirmishGame.cs:281).
- Hash and desync path: `PlausibleHash` bounds tick, interval and once per peer and tick; the host compares each client with its own `HashAt` and pauses on the first mismatch; resync is sent only after the host is paused and drained, and the reliable stream order (chunks, then Resume) means a client always has the whole save before it can start the countdown.
- Client leaves or times out mid-game: the host drops it (manual 10 s, auto 60 s), an AI takeover driver issues from the drop through the normal bundle path (deterministic), commands from a dropped peer are ignored, a peer gone at Start is dropped on the first update (M9-14).
- Lobby: slot requests are range-decoded (faction, colour, team, slot) and can only touch the sender's own slot or an open one; host-side names are cleaned and made unique; chat `FromPeer` is set by the host; custom map download is bounded (1 MB, 1000 chunks, hash checked against the lobby), file names reject `/ \ : ..`, and `MapFile` limits the map size before allocating layers.
- Setup/Lobby blobs: strict decode with versions, bounds and "no trailing bytes"; duplicate peers and slots rejected.
- LLM keys: stored per provider with DPAPI, never in settings, never in logs or error strings (`ProviderHttp` returns fixed reasons; only a 400/404/422 `error.message` is appended, cut to 200 chars; 401/403 are never appended); `KeyPolicy.MaySendKey` refuses plain http except to loopback and runs before the request is built in both providers; `ToString` of the stores hides the key; no Console output in src/Llm or src/Net.
- LLM replies: `ReplyParser` is strict on ranges (posture, focus, mix, target, cells <= 4095, at most 4 orders, minute <= 600, tech tier 2..5), never throws, has JSON depth protection from JsonDocument, and `say` is cleaned and cut to 200 chars; `DirectiveCodec.Clamp` rejects a target equal to the commander itself, out of range or neutral; the sim re-validates focus cells against vision.
- LLM commands for the wrong player: commands are built with the driver's player id for that commander (`CommanderOrders.TakeOrderCommands(execTick, player, ...)`), the host AI path stamps through `TrySubmitTrusted`, and clients never attach commanders (`CreateNetworked(..., setup.IsHost ? settings : null)`); the player's own chat goes to the prompt only and the prompt is built from the fogged `PlayerView`.
- Provider timeouts: one linked CancellationTokenSource covers send and body read (default 20 s, 5..600), cancellation by the commander is honoured, all HTTP/JSON failures return a failed ChatResult, and a failed call only sets the commander offline until the next success.
- Persona and providers data: loaders never throw, a bad file falls back to built-in defaults; personas contain no "Secret" lore paragraphs.
