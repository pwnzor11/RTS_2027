# Lens B: Simulation performance at scale and shape for M2-M4

## Findings (ranked, most dangerous first)

### B-1 · Every per-kind system hard-codes three stores; "Aircraft" in the docs does not exist in code · severity: COSTLY-LATER
- Evidence: `ActorKind` is `Vehicle, Infantry, Building, Projectile` (Core/ActorKind.cs). Architecture §3 promises an Aircraft store. In `Simulation*.cs` the three-way kind switch / triple loop is repeated in `StoreOf`, `TryResolve`, `TryGetActorInfo`, `WeaponOf`, `SightOf`, `PlayerOf`, `ShooterPos`, `Hurt` (twice), `Detonate` (three loops), `AcquireTarget` (three loops), `RunCleanup`, `UpdateVision` (three loops), `Snapshot`, `RunCombat`, `OnCombatActorRemoving`, `CombatState` (`new[]{veh,inf,bld}` indexed by `(int)kind`). `Command.Arg` is overloaded as "subject kind" (0/1 only) for Move and as "type index" for Place.
- Failure: The first new actor class (aircraft in M3, harvesters are fine because they are vehicles, but Lua-spawned crates/civilians/walls/capturable buildings are not) means editing about 15 sites. Missing one produces a silent bug, not a compile error: for example an aircraft that cannot be targeted, never reveals vision, or leaks `AttackTarget` refs after death. Nothing is trait-based: behaviour is `MissionHandlers` table (good) plus per-kind `switch` (bad). There is no component or trait mechanism. Docs §3 says "component structs in parallel arrays", but code is fixed per-store SoA with a `MobileStore` base.
- Fix: Before adding any 4th kind, introduce one `IActorStore` view (Player, TypeIndex, Position, Health, Slots, Armor/Sight/Weapon lookup by type) and one `ForEachAlive(kind)` helper. Route AcquireTarget, Detonate, Hurt, UpdateVision, Snapshot, and combat cleanup through it. Make `CombatState` store-sized by a list of stores. Do this as the first M2 task, while there are only 3 kinds. When: NOW (before M2 production adds spawns), cost M.

### B-2 · No alliance, neutral or team concept; "enemy" is `owner != player` everywhere · severity: WILL-BREAK (M3/M4)
- Evidence: `AcquireTarget` (`_units.Player[i] == player` skip), `IsValidTarget`/`IsEnemy` (`info.Owner != player`), `Detonate` (`!wh.HitsAllies && Player == owner`). `grep Alliance|Team|Neutral|IsAlly` in src/Sim returns nothing. `VisionState` is strictly per-player with no shared vision. Design §7 of architecture wants "ally moving / ally stopped" blockage tiers and 8-player skirmish with AI helpers; campaign needs civilians, neutral tech buildings, and ally reinforcements.
- Failure: In 4v4 or any campaign with an allied faction, allies auto-attack each other, splash "hits allies" by owner only, fog is not shared. Retrofitting after AI and Lua exist means touching every comparison above plus saves, replays and hashes (a team table is new sim state).
- Fix: Add `PlayerInfo[]` sim state part (team id, neutral flag, shared-vision flags, later credits/power/tech) and a single `Relation(a,b)` (Self/Ally/Enemy/Neutral). Replace the `!=` checks. Make the vision update OR allied counts. When: NOW, before M2 AI, cost M.

### B-3 · Per-player state and economy have no home; type table is shared and read directly · severity: COSTLY-LATER
- Evidence: `RunEconomy/RunProduction/RunAiBookkeeping/RunTriggers` are empty stubs, correctly ordered in `Step`, but `_parts` has no per-player part (credits, power, queues, tech set, AI memory). Architecture §6 says Effects apply "to a per-player copy of the type table", yet code reads `Setup.Rules.Vehicles[typeIndex]` directly in about 20 places (`Hurt`, `SightOf`, `Aim`, `LocoOf`, `UpdateVision`, `StatsOf`). `_parts` ordering is append-only and comment-locked.
- Failure: Upgrades (design 02 §5, "8-12 per faction") and `Tech.Grant` cannot be implemented without a mass edit of those reads. Production/economy bolt on cleanly in the tick order, but only once the player-state part exists. Harvester state machine fits `MissionKind` and handler table (this is fine).
- Fix: Add `Simulation.RulesOf(player)` (returns a per-player type-table view, initially the shared table) and use it in all type lookups now. Add `PlayerState` part now (even if empty). When: NOW/before M2, cost S-M.

### B-4 · Fixed capacities that throw or silently drop, with 8-player skirmish · severity: WILL-BREAK (M3)
- Evidence: `SlotArray.Allocate` throws `InvalidOperationException("SlotArray is full.")`. Capacities: units 2048, infantry 2048, buildings 512 (`BuildingStore.DefaultCapacity`), projectiles 1024 (`Fire` silently returns false when full). `VisionState.GhostCapacity = 512` is tied to building *indices*; `CheckGhostIndex` throws beyond. Map max 128x128 (`MapData` check). `CombatState` and `VisionState` are sized separately from the stores (`actorCapacityPerKind = 2048` default in Vision ctor, not tied to the store), so changing one capacity without the others corrupts or throws. Save format embeds capacity and rejects mismatches.
- Failure: Production (M2) spawns via an allocation that throws mid-`Step`; in lockstep this kills the host and every peer at the same tick. 8 players x about 50 buildings (turrets, walls-as-buildings, power) hits 512 at M3. Raising capacity later invalidates saves and replays.
- Fix: Make `Allocate` return `EntityId.None` and have production refuse to start/queue (and AI see "pop full"). Define a pop cap per player in rules. Derive Vision/Combat capacities from the store objects. Decide capacities from a single `SimLimits` record in `SimSetup` (hashed). When: before M2 production, cost S.

### B-5 · Path requests are per-unit and FIFO with latency proportional to queue; cache is useless once buildings churn · severity: COSTLY-LATER (M2-M3 feel)
- Evidence: `PathService.Process` budget 4000 expansions/tick, FIFO, `_queue.RemoveAt(0)` is O(n), `Poll` scans the queue linearly for every pending unit every tick. `CombatMissions` chase and `MoveMission.Follow` (line 182, 207) issue single `Request` per unit; only same-tick same-goal `Move` commands get a shared group search (`StartPendingMoves`). Cache key includes `_map.Version`, which `SetBuilding` bumps on every placement/removal, so all entries die with each building event; and a cache hit "charges the cost of the original solve" (so it saves CPU, not latency). `PathVersion != map.Version` triggers revalidation of the remaining route for every moving unit after any building change. `Solve` also allocates `new bool[w*h]` per group request and `Entry`/arrays per request.
- Failure: 8 AIs building continuously plus waves of 100+ units on AttackMove chase different targets; each long A* costs roughly 2-10k expansions, so the queue backs up to seconds of latency and units visibly stall. Not a determinism risk, a feel risk; the AI has no way to know. Cost scales with units x repaths, no flow field per destination.
- Fix: (a) Make `_queue` a real queue and index pending ids in a dictionary; (b) cache keyed by a coarser region version or invalidate only when a changed cell lies near the path; (c) have AI attack waves issue `Move` batches (shared group search already exists) and have AttackMove chase reuse the group id; (d) pool the scratch arrays. Profile first (see Unknowns). When: before M3, cost M.

### B-6 · Target acquisition and splash are O(all actors) with no spatial index; Lua triggers and AI will need the same query · severity: COSTLY-LATER
- Evidence: `AcquireTarget` loops all 2048+2048+512 slots (building pass also loops footprint cells and visibility). Guards rescan every 15 ticks, AttackMove every 5 (`AttackMoveScanTicks`), and `WakeOnHit` resets the scan. `Detonate` with splash loops all three stores per impact. `OnCombatActorRemoving` loops all actors plus projectiles on each death. `CanPlace` loops all units/infantry to find blockers. `UpdateVision` per tick loops 4600 slots, then per player x all buildings with `FootprintVisible`, plus `GhostsFor()` allocates a `List` of up to 512 per player per tick.
- Failure: With 1500 units on attack-move, about 300 scans/tick x about 4500 = 1.4M distance checks per tick, tolerable at 50 ms budget on a desktop but leaves nothing for AI and Lua. Lua `OnEnter(zone)` / `OnIdle` / AI "enemies near cell X" are the same query; without a spatial grid each costs a full scan. Per-tick allocations (ghost lists, path Req/Entry, `StartBatch` arrays, `Snapshot` lists) will cause GC hitches on low-end Windows machines.
- Fix: One deterministic cell-bucket index (cell -> chain of EntityIds, rebuilt or incrementally maintained in slot order) exposing `ForEachInRadius(center, r)`. Use it in AcquireTarget, Detonate, triggers, AI. Replace `GhostsFor` list with a span/iterator. When: before M3/M4, cost M.

### B-7 · AI query surface is not defined; honest-fog AI is by convention only · severity: COSTLY-LATER
- Evidence: Stores expose public mutable arrays (`public readonly byte[] Player` etc.); `Snapshot(viewer)` allocates the whole visible world as a `List<UnitView>` each call; `RunAiBookkeeping` is a stub. Nothing exposes per-player aggregates (my unit count by type, known-enemy list with timestamps, resource fields near cell).
- Failure: An AI written against raw stores reads omniscient state (violates design pillar 4 "honest AI") or calls `Snapshot` repeatedly (allocation and O(N)). Determinism is not at risk (AI runs in `Step`), but difficulty tiers need cheap information-age limiting.
- Fix: Define a read-only `PlayerView` struct (fog-filtered enumerators, spatial index from B-6, last-seen memory kept in sim state) as the only thing AI code may reference; enforce with an analyzer or by putting the AI in a separate assembly that sees only the interface. When: before M2 AI, cost M.

### B-8 · Hard-coded 2-player assumptions: none found, but walls/overlays and `Command` payload are not ready · severity: CHEAP-WIN
- Evidence: No `player == 0/1` literals found; player is `byte`, vision supports up to 255 (`VisionState`), per-player arrays are sized by `PlayerCount`. But `Command` has one `Arg` int overloaded per kind (Move: subject kind; Attack: two kinds packed in bits; Place: type). Build/Cancel/Rally/Special/Harvest and "factory subject + type + queue" need two ints plus a cell.
- Failure: Each new command invents another bit-packing convention in `OwnsSubject` style helpers; replays recorded from M2 will bake them in (replay format already versioned but commands persist).
- Fix: Widen `Command` once now (Arg, Arg2) and define per-kind payload in one table next to `CommandKind`. When: NOW, cost S.

### B-9 · Hash cost and GC: whole-state serialization into a fresh MemoryStream every 16 ticks · severity: CHEAP-WIN
- Evidence: `ComputeStateHash` writes all parts (vision counts 16384 cells x players x 2 bytes, 4 x 2048 actor slots, 25 SoA arrays per mobile slot with dead-slot flags) into a new `MemoryStream`, then `XxHash64`. `ComputeSubHashes` does the same per part. Combat `Write` enumerates 4600 entries.
- Failure: Probably about 1-3 MB per hash with LOH-sized buffers every 0.8 s: periodic GC pauses in the render thread when the sim runs on it. Hash ring and LAN checks make this permanent.
- Fix: Reuse one pooled buffer / stream, or hash incrementally with `XxHash64.Append` through a small writer. When: before M5 (cheap now), cost S.

## Things you checked that are fine
- Tick order in `Step` matches doc (input, missions, movement, combat, economy, production, AI, triggers, cleanup); economy/production slot in cleanly after combat.
- Slot allocation is lowest-free-index with generations; `EntityId` validation on use; iteration by index; no hash-map iteration in sim (cache is lookup only, `SortedDictionary` for results).
- Vision is incremental (disc add/remove per moved actor), not a full-map recompute; one comparison for unchanged actors.
- Mission handler table with `WakeTick` sleeping avoids polling idle units each tick.
- Path expansion budget with debt carry-over is deterministic and independent of cache state.
